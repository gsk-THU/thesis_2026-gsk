**实验要求**: ch3 中，我们的系统已经能够支持多个任务分时轮流运行，我们希望引入一个新的系统调用 sys_trace （syscall ID: 410）用来追踪当前任务系统调用的历史信息、并进行任务内存的读写。定义如下：

int sys_trace(int trace_request, unsigned long id, uint8_t data);
syscall ID: 410

调用规范：
这个系统调用有三种功能，根据 trace_request 的值不同，执行不同的操作：

如果 trace_request 为 0，则 id 应被视作 uint8_t * ，表示读取当前任务 id 地址处一个字节的无符号整数值。此时应忽略 data 参数。返回值为 id 地址处的值。

如果 trace_request 为 1，则 id 应被视作 uint8_t * ，表示写入 data （作为 uint8_t，即只考虑最低位的一个字节）到该用户程序 id 地址处。返回值应为0。

如果 trace_request 为 2，表示查询当前任务调用编号为 id 的系统调用的次数，返回值为这个调用次数。 本次调用也计入统计 。

否则，忽略其他参数，返回值为 -1。

说明：
uint8_t 是C语言中的标准类型，表示一个无符号的8位整数。在代码中你可能需要使用 uint8 替代。

你可能会注意到，这个调用的读写并不安全，使用不当可能导致崩溃。这是因为在下一章节实现地址空间之前，系统中缺乏隔离机制。所以我们 不要求你实现安全检查机制，只需通过测试用例即可 。

你还可能注意到，这个系统调用读写本任务内存的功能并不是很有用。这是因为作业的灵感来源 syscall 主要依靠 trace 功能追踪其他任务的信息，但在本章节我们还没有进程、线程等概念，所以简化了操作，只要求追踪自身的信息。

## 问题 1 [UNDERSTANDING]

在 case 0 和 case 1 中，内核直接解引用了用户传入的 `id` 作为指针进行内存读写。这种实现方式在操作系统中存在什么潜在风险？结合课程知识库中提到的"ch3 中还没有实现地址空间"这一背景，解释为什么实验允许这种不安全的实现，以及在未来章节（如 ch4 实现地址空间隔离后）需要如何改进才能确保内核安全？

**参考代码**:

```
uint64 sys_trace(int trace_request, unsigned long id, uint8_t data)
{
	struct proc *p = curr_proc();
	switch (trace_request) {
	case 0:
		/* 读取当前任务 id 地址处一个字节 */
		return *(uint8_t *)id;
	case 1:
		/* 写入 data 的最低位字节到 id 地址处 */
		*(uint8_t *)id = data;
		return 0;
	...
	}
}
```

**出题理由**: 考察学生对内核/用户态内存隔离、地址空间概念的理解。学生需要认识到直接解引用用户指针可能导致内核崩溃（访问非法地址）或安全漏洞，并理解当前章节缺乏内存隔离机制的现状，以及未来需要通过页表权限检查、地址合法性验证等机制来修复这一问题。
